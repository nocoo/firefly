# 公开内容缓存、监控过滤与 D1 用量监控

2026-09-18，目标版本 **v2.14.0**。应用缓存、过滤、索引迁移与采样脚本已实现；发布后的部署证据追加在本文末尾。上线前依据见 [D1 用量审计](32-d1-cost-audit-2026-09.md)。

本次实现“监控不入库 + 公开内容跨请求缓存 + 写入后主动失效”。当前 Railway 生产环境只有一个服务、一个运行副本，没有项目内 Redis 服务，也没有 Redis/Upstash 连接变量。第一版使用 Next.js 自带 Data Cache；增加副本、需要跨部署共享缓存，或已有合适的共享 Redis 时，再接 Redis 后端。

## 实际在查询什么

| 入口 | 当前查询及问题 | 缓存对象 |
| --- | --- | --- |
| 首页、分页、分类、标签、归档 | `listPosts` 每次执行文章联表查询；只有总数有 5 分钟缓存 | 规范化筛选条件对应的文章列表与总数 |
| 文章页、公开文章 API、Markdown 文章 | 正文、文章标签；文章页还查上一篇/下一篇和评论 | 已发布正文、标签、相邻文章、公开评论 |
| 页面标题、导航、SEO | 设置和分类列表已有短缓存，默认作者仍重复读取 ID 和资料 | 公开站点设置、作者显示资料、分类/标签/归档 |
| 404 | 查询最近 5 篇文章 | 共用固定的最近文章缓存，与错误 URL 无关 |
| RSS、sitemap、Markdown 首页 | RSS 只有独立的 60 秒进程缓存；sitemap 通过文章列表读取完整内容；Markdown 首页取 250 篇后只展示 30 篇 | 分别缓存输出或所需的精简数据；Markdown 只取 30 篇 |

首页的 [JournalIntro](../src/components/blog/journal-intro.tsx) 调用 `connection()`，为每次请求选择随机场景；文章页通过 `isAdminSession()` 读取会话。这些动态渲染路径仍会执行数据库函数。根布局的 `revalidate = 300` 无法自动把它们变成跨请求的查询缓存。文章页现有 React `cache()` 只去重同一次渲染中的请求。

生产实测，默认列表返回 10 篇却读取 1,976 行。近 7 天各类列表查询合计 31,698 次、约 5,932 万行读取。缓存命中可以省掉整次查询；缓存未命中仍要用审计提出的索引优化。这个统计包含不同用途的列表，不能全部算成公开页面缓存的可节省量。

## 1. 在写入之前过滤监控

- 在 [机器人识别](../src/models/analytics.ts) 增加不依赖具体版本号的 Uptime Kuma 规则，归类为 `monitor`。
- 在 [埋点入口](../src/lib/tracking.ts) 先识别并跳过 `monitor`，然后才获取数据库、解析文章 ID、计算 IP 哈希。只改成 `is_bot = 1` 仍会插入事件，省不了写行。
- 在 [proxy](../src/proxy.ts) 只为真实导航的 GET 记录 PV，跳过 HEAD 和明确标记的预取请求，如 `next-router-prefetch`、`Purpose: prefetch`、`Sec-Purpose: prefetch`。不排除实际 RSC 导航。`next.config.ts` 设置 `skipProxyUrlNormalize: true`，防止 Next 在 proxy 前移除预取头；原始 admin RSC/data 路径仍保留鉴权。此行为已经真实 HTTP 验证。
- 监控访问旧地址时也跳过 `redirects.hit_count` 更新。过滤只影响计量，原有鉴权、限流、页面响应和重定向照常执行。
- Kuma 主探测改到 `https://lizheng.blog/api/live`；若仍需检查整页渲染，可保留低频首页探测。该健康接口已经验证不写访问事件，数据库探针读写行数均为 0。现有 Kuma 凭据未通过认证，监控配置尚未修改；应用侧过滤不依赖这个操作。

近 7 天 Kuma 占 10,072 / 19,014 = **53.0%** 的访问事件。每条事件维护表和索引共写 7 行，因此阻断新增可减少约 **1,439 条 INSERT / 天、10,072 个计费写行 / 天**，另省首页渲染读取。

Google、AI 等爬虫仍正常获取内容，第一版保留现有爬虫报表。若以后决定不需要这类报表，可以同样在入口停止逐条记录；按本次 7 天分布，连同 Kuma 共占事件约 73.4%。不能将该比例直接称为全库写行降幅。

已有 Kuma 记录不会因新过滤规则消失。历史看板的公共时间范围条件统一排除 `Uptime-Kuma/%`，包括总量、真人、来源、趋势及前周期比较，且保留 `user_agent IS NULL` 的记录；同时应用审计中的时间范围索引优化。不批量修改或删除历史记录来纠正显示，避免额外写入和不可逆的数据清理。

## 2. 缓存公开数据，写入后让下一次访问重新加载

第一版沿用当前未启用 Cache Components 的 Next.js 配置，通过 `unstable_cache` 包装明确的公开数据读取函数。该 API 在安装的 16.3.5 中仍可用；官方推荐的新 `use cache` 需要启用 Cache Components，本次无需扩大为渲染模式迁移。

缓存路径为：访问页面 → 读取公开数据缓存 → 未命中时查询 D1 并保存。缓存命中不再查询对应内容表，真人访问统计仍按现有策略写入。

具体约定：

- 公开读取接口固定 `status = 'published'`。后台编辑、预览、管理员/作者 MCP 的私有读取、令牌验证和健康探针继续使用原来的即时读取接口。共享缓存只保存公开所需字段，不保存会话、作者私有邮箱或评论者邮箱。
- 列表键包含分类、标签、归档、页码、每页数量及排序，先校验并规范化参数。缓存命名空间包含环境和结构版本，不把数据库对象、令牌或请求头作为参数。已发布文章按 slug 缓存，标签和评论按文章 ID 缓存。
- 普通内容采用 **1 小时重新验证周期 + 内容变更主动失效**。定时重新验证按访问触发，不设扫描全站的定时任务。它是兜底刷新机制，不是数据库故障时“最多旧 1 小时”的硬保证。
- 第一版给公开内容统一使用 `public-content` 标签。文章、作者、分类或站点设置改变时统一失效；只有 494 篇已发布文章，暂不维护复杂的依赖关系。失效后按需重建被访问的条目，不立即重读全站。
- 现有 count/settings/taxonomy/feed 的进程缓存不能简单叠在新缓存内部。公开入口使用无旧 TTL 缓存的加载函数，避免清掉外层后又把旧内层结果缓存一小时；后台可保留其现有接口。缓存原语放在 `src/data/core/`，写后协调放在服务层。
- React `cache()` 继续负责请求内去重。对同一键并发冷启动，复用正在执行的加载 Promise；失败不缓存，并测试写入与回填交错时旧结果不会重新成为有效缓存。不能假设 `unstable_cache` 自动合并所有跨请求冷启动。
- 未知 slug、无效页码、随机查询参数不能无限创建长期条目。无效页码/页大小归一为安全默认值、每页最多 100 条；每代缓存最多登记 2,048 个内容键，超出时直接读取；404 共用固定最近文章缓存。不存在文章可用最多 256 项、30 秒的短期负缓存并在内容变更时清除；搜索结果先沿用即时查询，不新增长期任意关键词缓存。
- RSS 需要正文；sitemap 使用精简字段查询，Markdown 首页只取 30 篇（原为 250 篇），避免读取全站正文。当前 Next 默认单个 Data Cache 条目有约 2 MB 限制，实施时检查序列化大小；列表精简主要节省传输和缓存空间，D1 读行下降仍靠缓存命中与索引。

当前公开页面没有展示 `view_count`。访问计数更新不触发 `public-content` 失效，否则每次访问都会使缓存作废。公开 API 若保留该计数，可接受内容缓存周期内的延迟；管理看板仍读即时统计。评论新增/删除属于展示内容变化，要触发失效。

## 3. 把所有公开内容写入接到同一失效入口

成功写入后调用统一失效函数，保留现有服务层“主写失败抛错、次要副作用失败记录错误”的约定。正常撤回和删除使用 `revalidateTag('public-content', { expire: 0 })`，使新的源站读取等待新数据，而不使用会先返回旧内容的 `max` 模式。Next 原生失效在应用内完成，不新增公开清缓存接口。

| 变化 | 当前需要接入的入口 |
| --- | --- |
| 发布、编辑、撤回、删除、批量修改文章 | [PostService](../src/services/post-service.ts)，覆盖 Web、管理员 MCP、受限作者 MCP |
| AI 生成摘要、保存引用卡片 | [MCP post 扩展工具](../src/lib/mcp/entities/post.ts) 的两处原本直接 `updatePost` 的写入已改走 PostService |
| 标签关联、分类/标签改名、删除、排序 | PostService、taxonomy Web 路由及 MCP 写入入口；保留原有输入映射和 hooks |
| 人类作者/AI 作者名称、头像、公开状态变化 | 管理作者路由、头像上传/删除路由 |
| 默认作者、站点名称、页大小、描述、评论开关、logo | settings 和专用作者/logo 写入入口 |
| 新增、回复、删除评论 | 评论写入路由，同时更新缓存中的列表计数和正文评论 |

标签、计数和 FTS 等后续写入完成后再做最终失效；次要写入失败也必须执行失效，不能因为失败而跳过。直接通过 SQL 客户端或迁移脚本改内容不会自动触发应用 hooks，需要显式清缓存或重启应用；重新验证周期只是补救。

RSS、Markdown、sitemap 目前还存在 `max-age=3600` 的浏览器/代理缓存。源站 Data Cache 失效无法撤销这些已经发出的响应。若要求新请求立即看见发布/撤回，内容响应使用 `max-age=0, must-revalidate`，检查并同步处理已有 CDN 缓存；图片和其他版本化静态资源继续长期缓存。已有打开的页面或已下载内容不会被撤回操作远程删除。

重定向映射和埋点的 slug → 文章 ID 解析属于 proxy 的其他读取路径。第一版保留其 5 分钟缓存，不把它们误算成公开内容缓存命中率；后续按实际命中和更新方式单独优化。缓存内容也不能消除所有 SQL：访问事件、后台操作和健康探针仍有各自职责。

## Redis 的使用边界

2026-09-17 23:06 UTC 只读查询 Railway：生产只有一个活动部署且状态为 `SUCCESS`，区域 `asia-southeast1-eqsg3a`、1 副本、0 持久卷；服务没有 Redis/Upstash 缓存连接变量。检查仅保留变量名称判断，没有输出变量值。

| 需求 | 选择 |
| --- | --- |
| 当前单实例，在运行期间减少重复 D1 查询 | Next 自带内存/本地磁盘缓存；无需新增服务。部署或重启丢失缓存时重新加载即可 |
| 多副本、多区域，或必须跨重启/部署共享缓存与失效 | 为同一组公开读取接口接 Redis 共享后端，协调标签失效；不能只清当前进程的 Map |

单副本不代表滚动部署期间永远只有一个进程。第一版不能声称跨新旧部署立即一致；若这一窗口也要求严格同步，应直接采用共享后端。接 Redis 时必须同步保存失效状态并处理本地缓存，不能只广播一次 Pub/Sub 通知；离线实例可能漏掉通知。Redis 不可用时公开读取可回源 D1，鉴权不依赖这个公共缓存。

本库近 30 天 D1 读写按超额单价折算约 **$1.15**，其中读取约 **$0.52**。公开读缓存能省的 D1 行费用只是读取部分的一部分，新增 Redis 月费需要与这项收益比较；另有减少 Worker 调用和请求延迟的收益，尚未折算。复用现有 Redis 可以考虑，为本库单独增加付费 Redis 不是当前首选。

## 落地顺序与验收

1. 先做监控过滤和统计口径修正。Kuma/HEAD/明确预取不调用数据库埋点；真人 GET 正常记录，搜索/AI 爬虫分类保留，鉴权与限流行为不变。即使 Kuma 地址暂时未改，应用侧也停止新增监控事件。
2. 接公开内容缓存和上述写后失效入口，同时覆盖首页、404、文章页、API、RSS、sitemap、Markdown。用隔离本地数据库和真实 Next 运行环境验证跨请求命中、Web/MCP 写后刷新、撤回/改 slug、评论和设置修改；单测用现有 `createMockDb()`，不能只 mock 缓存 API 就宣称失效有效。
3. 应用审计已验证的列表索引和统计时间条件优化。迁移为独立操作，先在隔离环境验证，线上用实际 `rows_read` 复核；保留冷启动和低命中场景的收益。
4. 上线前完成项目要求的类型、lint、覆盖率和相关集成/浏览器检查；重点覆盖并发回填、失败、过期、重启，以及公开缓存绝不复用草稿/管理员结果。不要使用生产数据库跑这些测试。
5. 上线后比较至少 3–7 个完整 UTC 日：Kuma 新增事件应为 0；观察公共列表/正文的缓存命中率、内容 SQL 次数、D1 读写行数。以“相同内容、无修改时，公开内容加载函数命中缓存后不调用 D1”为验收条件；全库下降比例以实际结果为准。缓存指标使用应用日志/平台指标，不逐请求写回 D1。
