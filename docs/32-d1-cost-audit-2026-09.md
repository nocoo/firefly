# Firefly D1 用量与成本审计 · 2026-09-18

最值得先做的是把每分钟的首页监控改到 `/api/live`，然后优化文章列表和统计查询。数据库约 183 MB，当前存储清理的省钱收益很小。本库近 30 天读写按 D1 超额单价折算约 **$1.15**，当前体积折算约 **$0.14/月**；这些是边际成本估算，不是账单金额。

通过 Wrangler、Cloudflare GraphQL Analytics 和 D1 REST API 只读检查生产 `lizhengme-db`，并对照当前 2.13.3 代码。线上 `/api/live` 返回 200、版本 2.13.3、数据库已连接。本次未修改生产 SQL、索引、数据或监控配置；候选索引只在独立本地 SQLite 中试验。当前环境没有可用 Navicat，使用的是同一生产 D1 的官方访问接口。

完整自然日窗口按 **UTC**：近 7 天为 9 月 10–16 日，近 30 天为 8 月 18 日–9 月 16 日；审计时北京时间已是 9 月 18 日，UTC 仍是 9 月 17 日。证据见 [聚合数据、SQL 与查询计划](32-d1-cost-audit-evidence.json)。

**1. 最高优先级：停止为首页监控记录访问事件**

近 7 天共保存 **19,014** 条访问，其中 **10,072 条**的 User-Agent 是 `Uptime-Kuma/2.3.2`，全部访问 `/`。每天 1,438–1,440 条，与每分钟一次探测一致，占所有事件 **53.0%**。历史累计已有 **254,448** 条 Kuma 记录。

这些记录全部被标成真人。原因是 [机器人识别](../src/models/analytics.ts) 没有 Uptime Kuma 规则；[代理埋点](../src/proxy.ts) 会记录首页请求，[写入函数](../src/data/analytics-record.ts) 每次插入一条事件。

生产 Query Insights 显示每次 `INSERT INTO page_views` 写 **7 行**：表记录 1 行、TEXT 主键索引 1 行、5 个二级索引各 1 行。因此监控这一项就对应 **每天约 10,072 行写入**，可以解释用户注意到的每天约 10K 的一个具体来源。每月约 30.2 万行写入，按超额单价约 $0.30，另有首页渲染引发的读查询。

建议把这个首页探测目标改为 `https://lizheng.blog/api/live`，保持现有探测频率。该地址已经验证可用，其 `SELECT 1 AS probe` 实测 **0 行读取、0 行写入**，且 `/api/` 不进入页面埋点。若需要检查整页渲染，可另保留低频首页检查。在埋点入口识别并跳过监控流量，可防止其他监控再次污染统计；仅把 `is_bot` 改成 1 仍然会逐条写库。

Kuma 保存的 API key 和登录凭据均未通过认证，因此未取得当前监控配置或监控 ID。上述目标地址、频率和数量来自生产访问记录；没有修改监控项。

其余访问中，当前已识别爬虫占 **3,885 条 / 20.4%**；扣除这些和 Kuma 后还剩 5,057 条，其中仍有脚本 UA，不能全部视为真人。对搜索和 AI 抓取，应先修复计量，再根据是否需要逐条留痕选择聚合或采样。

| 文章列表，含不同筛选条件 | 31,698 | 59,320,103 |

Query Insights 来自自适应聚合数据，与数据库级用量不完全对齐；这里用于定位热点，账单估算使用前面的数据库级行数。

[列表查询](../src/data/entities/post-queries.ts) 按 `status` 过滤，再按 `published_at, created_at` 排序。现有单列索引导致查询先处理全部已发布文章及关联数据，再进行临时排序。[404 页面](../src/app/not-found.tsx) 也会调用它取最近 5 篇文章，因此不存在的路径同样可能触发这项开销。

生产只读对比使用相同参数 `published / LIMIT 10 / OFFSET 0`：

| 方案 | 读取行数 | 返回条数 | 结果 |
| --- | ---: | ---: | --- |
| 当前查询 | 1,976 | 10 | 使用 `idx_posts_status`，临时排序 |
| 指定现有发布时间索引做对照 | 43 | 10 | 与当前结果完全一致，减少 97.82% |
| 仅减少 SELECT 字段 | 1,976 | 10 | 减少传输量，但计费读取行数不变 |

建议的候选索引如下，**未在线上执行**：

```sql
CREATE INDEX idx_posts_status_published_created
ON posts(status, published_at DESC, created_at DESC);
```

使用生产的 882 条索引相关字段在独立本地 SQLite 重建后，该索引消除了临时排序，返回结果保持一致；本地索引约 28 KiB。这个结论验证查询计划，不能把本地执行步数当成 D1 计费行数。上线后仍应以真实 `rows_read` 复核，覆盖首尾页和分类/标签筛选。

首页和 404 页的“最近文章”也适合复用现有短期缓存，发布/撤回文章时失效，进一步减少重复 SQL。相邻文章查询可随后评估 `(status, published_at, id)` 索引及 `(published_at, id) < (?, ?)` 的元组范围条件；本地已验证能直接按索引取相邻记录。

**3. 统计查询：改时间范围，并确认优化器选对索引**

[共享条件](../src/data/analytics-helpers.ts) 当前对每条记录执行 `date(viewed_at, 'unixepoch')`，使现有时间索引无法直接用于范围过滤。应保留当前“UTC 完整自然日、排除今天”的口径，改为：

```sql
-- 当前周期，参数仍为 days
viewed_at >= unixepoch('now', 'start of day', '-' || ? || ' days')
AND viewed_at < unixepoch('now', 'start of day')

-- 上一周期，两个参数仍都为 days
viewed_at >= unixepoch('now', 'start of day', '-' || (2 * ?) || ' days')
AND viewed_at < unixepoch('now', 'start of day', '-' || ? || ' days')
```

生产只读实测，均查询相同的 30 个完整 UTC 日：

| 查询 | 当前读取行数 | 修改后读取行数 | 降幅 |
| --- | ---: | ---: | ---: |
| 总量及流量来源聚合 | 475,258 | 85,703 | 81.97% |
| 真人浏览器分布，仅改时间条件 | 450,814 | 450,814 | 0% |
| 真人浏览器分布，改条件并指定现有时间索引验证 | 450,814 | 154,717 | 65.68% |

所有对比返回结果完全一致。第二行尤其重要：优化器仍选 `idx_page_views_bot` 扫描历史真人记录，**仅改日期表达式不保证降低所有查询的读行数**。

建议先改共享条件，再执行受控的 `PRAGMA optimize` 并检查实际计划。本地按真实日流量和真人/爬虫数量构造的数据，在更新规划统计后会选择现有时间索引；这个本地结果不保证生产行为。如果实际计划仍不理想，再考虑把现有 bot 索引替换为 `(is_bot, viewed_at, bot_category)`，并复核所有来源详情查询。这样可以保持索引数量，而不是直接给高频写入表叠加索引。

统计概览已有 8 个聚合查询，真人详情另有 8 个及文章标题查询；查询不含今天，结果变化慢，适合用现有进程缓存短期复用，以 UTC 日期、天数和来源作为缓存键，继续在缓存访问前验证管理员权限。

**4. 写入和存储的后续优化**

- `session_id` 在约 47.5 万条记录中全部为空，当前应用也没有按它读取。删除 `idx_page_views_session` 是清晰的候选：每条事件从 7 行写入降到 6 行，减少 14.3% 的事件插入写行。按近 7 天流量约省 2,716 行/天；先移除 Kuma 后，剩余收益约 1,277 行/天。以上收益有重叠，不能直接叠加。
- MCP 每次验证成功都会更新 `last_used_at`，近 7 天约 4,790 次写入。可利用已经读出的时间戳，把使用时间更新节流至 5–15 分钟；令牌验证和撤销检查继续执行。
- 默认作者 ID 和作者资料近 7 天合计约 81,632 次读取。这些查询每次只读一行，对 D1 行费用影响很小，但可通过复用 `settings.defaultHumanId`、请求内去重和公开资料缓存减少 HTTP/Worker 调用。
- 30 天以前的 `page_views` 有 386,161 行，90 天以前有 238,882 行。当前统计最长支持 365 天，还比较前一周期；直接清理会改变报表。若以后采用 30/90 天保留期，应先补齐历史聚合与归档，并单独处理跨日独立访客去重，不能把每日 UV 直接相加当周期 UV。

当前存储的超额单价折算仅约 $0.14/月；删除数据、构建索引本身也可能产生计费读写，删除后的空间回收还需要验证。因此先停止无效增长，再评估历史清理。`daily_stats` 为空且 `site_daily_stats` 停更，现阶段并没有可直接替代原始记录查询的完整日汇总。

**成本边界与建议顺序**

查阅当日 Cloudflare 官方定价：Paid 包含每月 250 亿行读取、5,000 万行写入、账号合计 5 GB；超出后分别为 $0.001/百万行读取、$1/百万行写入、$0.75/GB·月。索引更新算写入，缩短行内容不会改变行计数，批量传输 SQL 也不会自动减少计费行数。

账号近 30 个完整 UTC 日合计约 **391.16 亿行读取、7,850.86 万行写入**；最后完整日 28 个数据库的大小合计约 **12.54 GB**。这些已超过公开套餐包含量，但没有取得订阅账单和实际续费日，不能据此还原本月账单。

Firefly 占该窗口账号读取约 **1.33%**、写入约 **0.81%**。本库读写边际价格计算为：

```text
519,061,314 / 1,000,000 × $0.001 = $0.5191
632,715 / 1,000,000 × $1         = $0.6327
合计                             ≈ $1.15 / 30 天
当前 0.183 GB 存储按超额单价折算   ≈ $0.14 / 月
```

实际存储账单取决于账期内使用量；上面没有计入 Workers、Railway、R2 或固定订阅费。要明显降低账号整体账单，还应另行检查其他数据库；仅账号汇总就显示 `pew-db` 与 `tongjinet-db` 分别贡献约 216 亿、163 亿行读取，本次没有检查它们的业务 SQL。

建议按“监控地址 → 文章列表索引 → 统计范围与查询计划 → 无用 session 索引”的顺序落地。前两项成本低、收益容易验证；历史清理和日汇总留到确有保留策略或增长需求时。

针对后续“过滤无效流量、内容变更时才刷新、是否采用 Redis”的需求，补充了 [公开内容缓存与监控流量过滤方案](33-public-content-cache-plan.md)。它明确了公开查询范围、Web/MCP 写后失效入口及当前单副本部署下的缓存选择；以上审计数据和未修改生产的状态保持不变。

本次保存的 34 条成功审计 SQL 合计约 479 万行读取、0 行写入，另外有一次初始 schema 检查；按超额读取单价不足 $0.005。自然日用量和 Query Insights 的统计窗口均在审计前结束，避免把本次测量当成业务热点。
